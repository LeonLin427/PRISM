# PRISM

Research code and retained analysis inputs for **PRISM: Empirical Analysis of
Android Privacy Remediation and SDK Risk Attribution Using Co-occurrence
Heterogeneous Graphs**.

This local release candidate contains the analysis of 217 notice events involving
212 applications. Its 433 static-feature JSON files represent the unique APKs
used in the analysis. The original APK binaries are not included and are no longer
available in the project archive. Reproduction therefore starts from the retained
features, not from downloading or re-extracting APKs.

The graph model profiles six violation categories within the reported-event
corpus. SDK scores prioritize manual review; they are not SDK-level ground truth.

Application names, SDK names, and original notice descriptions remain in Chinese
where they serve as data identifiers or source labels. Python comments,
docstrings, and model CLI help are in English. The attribution and OOD Markdown
reports use English explanations while retaining the original identifiers.
Some other diagnostic reports, console messages, and source-language plots
retain Chinese text.

## Environment

The recorded run used Python 3.11.15 on Windows and CPU execution, with PyTorch
2.11.0+cu128, NumPy 2.4.6, pandas 3.0.5, SciPy 1.17.1, scikit-learn 1.9.0,
Matplotlib 3.11.1, and openpyxl 3.1.5. A CUDA-enabled PyTorch installation was
present, but these experiments use the CPU.

The supplied `environment.yml` records the core environment. With Conda:

```bash
conda env create -f environment.yml
conda activate android-privacy-sdk-analysis
```

Package availability depends on the configured channels and platform; this file
is an environment specification, not a cross-platform lockfile. Alternatively,
create a Python 3.11 environment and install `requirements.txt` with pip.
The release was checked in the existing recorded environment; installation into
a new environment has not been tested.

```bash
python -m pip install -r requirements.txt
```

Androguard is needed only for optional fresh APK extraction. It is not required
for any reproduction command below. Figure rendering uses Times New Roman when
available and falls back to DejaVu Serif.

## Start here: check the supplied release

Run from the repository root:

```bash
python verify_release.py
python run_pipeline.py --stage validate
```

The first command checks the release checksums, input counts, stored application
group splits, ensemble AUCs, and 156 nonconstant feature/category tests.
The second also runs the SDK-matching, differencing, and training-seed regression
tests, compares the cached graph builder with the full edge table, and checks the
temporal/SDK-holdout split constraints. It rebuilds the disposable graph cache
locally if necessary. It does **not** run a full model evaluation.

To regenerate Figures 3--7 from the supplied paper reports:

```bash
python run_pipeline.py --stage figures
```

Images are written to `figures/` inside this repository. Figures 1 and 2 are
manually prepared conceptual illustrations and are not generated by this release.

## Reproduce analyses from retained features

Work in a separate checkout/copy if you want to retain the supplied working
outputs. The `reference/` directory is never an output target of the runner.

```bash
python run_pipeline.py --stage prepare
python run_pipeline.py --stage baseline
python run_pipeline.py --stage main --run-name main_reproduction
python run_pipeline.py --stage attribution
python run_pipeline.py --stage ood
python run_pipeline.py --stage figures
```

Or run those stages in sequence:

```bash
python run_pipeline.py --stage all --run-name main_reproduction
```

Stage behavior:

- `prepare`: verifies the released label mapping, matches SDKs, rebuilds both
  feature tables, performs the association tests, and builds the heterogeneous graph.
- `baseline`: evaluates issue/remediated version discrimination.
- `main`: runs the eight model variants using five folds, three split repetitions,
  three model seeds, 300 epochs, and one CPU thread. Full outputs are written to
  `runs/<run-name>/`; its summary/report are copied to `out/` for plotting.
  Existing run directories are rejected rather than overwritten.
- `attribution`: trains the full-corpus attribution models with self-checks.
- `ood`: first verifies split constraints, then runs temporal and SDK holdout tests.
- `figures`: plots the results currently in `out/`.

These commands overwrite derived tables and working reports, not the retained
feature JSON files or `reference/`. A complete run is substantially slower than
validation. Main CV uses model seeds **1000/1001/1002** and split seeds **0/1/2**;
attribution and OOD use **1000/2000/3000**. The phases intentionally have different
seed schedules. Exact floating-point reproduction across platforms is not assured.

Direct entry points remain available, for example:

```bash
python train_gnn.py --output-dir runs/another_run --threads 1 --rebuild-cache --verify
python interpret_gnn.py --selfcheck --threads 1
python eval_ood.py --verify
python eval_ood.py --threads 1
```

Do not use `--quick` outputs as paper results.

| Attribution and stability | `interpret_gnn.py` | `reference/out/m4_report.md`, `reference/out/sdk_attribution.xlsx` |
| Temporal/SDK holdout | `eval_ood.py` | `reference/out/m5_report.md`, `reference/out/m5_results.xlsx` |

The filenames `m4_report.md` and `m5_report.md` are retained for compatibility
with the analysis outputs. They summarize SDK attribution/stability/cases and
temporal/SDK-holdout evaluation, respectively. The Markdown files are for human
inspection, not training inputs; their Excel companions contain structured
results used by the plotting code. `out/` holds working copies, while
`reference/out/` preserves the paper results.

`reference/main_cv/gnn_run_manifest.json` records the original run settings and
input/code hashes. Machine-specific paths were normalized for distribution;
the original recorded hashes were not changed. The original cache hash is retained
as provenance, although the cache itself is omitted. Pickle caches are generated
locally; do not load pickle files from untrusted sources.

`SHA256SUMS.json` describes this release candidate, rather than the historical
training run. Source hashes can differ from that run's manifest because of the
packaging and English documentation changes described in `RELEASE_NOTES.md`;
the original historical hashes remain intact. Regenerable working tables,
`graph/`, `out/`, figures, and
caches are excluded; retained inputs, source code, and `reference/` are checked.

## Data scope and interpretation

SDK identification uses conservative one-way package/component matching plus
other retained signature evidence. Deep package signatures may be missed when
only shallow DEX prefixes remain. Sensitive API features count method-name
occurrences, not runtime invocations. API differences use **issue minus remediated**
counts, with the maximum over versions on each side of an event.

The primary modeling unit is a notice event. Splits group all events from the same
application; auxiliary SDK-list markers are excluded from predictive inputs.
Remediation features are retrospective. The original binaries cannot be used here
to independently repeat the extraction or recover missing fine-grained features.
